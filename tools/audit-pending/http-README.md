## Isolation controls

`http-run.mjs` creates a fresh timestamped directory under the Git-ignored evidence root. It rejects occupied ports or an existing run directory. It starts only the already installed PostgreSQL binaries, creates a new database and checks `SHOW data_directory`, database, role, host and port before any fixture write.

Fixed SQL target: `127.0.0.1:55441`, role `rivya_http_qa`, database `rivya_http_disposable`. The connection-string hostname is `localhost` only because the Neon client derives its HTTP endpoint from that string; `http-transport.mjs` sends SQL exclusively to the fixed numeric-loopback target. Existing QA on port 55439 is neither queried nor changed by this harness. Schema comes from reviewed repository SQL, followed only by generated fictional staff/inquiry records. It copies no private records or provider tokens.

`http-server.mjs` serves the existing Next build directly over `https://127.0.0.1:4207` with a one-day self-signed certificate generated by installed Git OpenSSL. There is no certificate-store change or global TLS relaxation. Browser certificate acceptance is scoped to its test context. Next's internal read-only redirect fetch is allowed only to that exact loopback origin with redirect following disabled. Database fetch is translated to actual local PostgreSQL; all other intercepted server fetch targets and all non-loopback browser requests are refused. **These are fetch/SQL/browser transport guards, not an OS-wide egress firewall.**

No Next cookie/cache implementation is stubbed. There is no fake or live cloud provider. The supplied production-mode indexing flags exist only in the isolated loopback process to exercise actual sitemap inclusion/withdrawal; canonical brand URLs in the XML are never visited.

The runner stops only its own process handles and exact new PG data directory in `finally`. It preserves evidence and does not recursively delete anything. Raw screenshots, synthetic DB files and logs stay in `test-results/`, ignored by Git.

## Run

From the repository root, after an appropriate build exists and no build is running, invoke installed Node 22 with `tools/audit-pending/http-run.mjs`. The runner deliberately uses the installed Node executable that invokes it and fixed existing PG/Chrome/OpenSSL locations. It refuses a concurrent build-ID change. No dependency installation is required.

The first harness attempts established two local configuration details: Next's fetch wrapper needs the Neon-derived endpoint to be a valid hostname, and a two-port TLS proxy causes local origin comparison to see the internal port. Both were corrected inside this harness; neither was an application-authentication defect. The retained final run has neither error.

Real provider upload/deletion, deployment/CDN caches, production Neon transport, native assistive technology and physical devices remain separate acceptance gates. This harness does not close them.
