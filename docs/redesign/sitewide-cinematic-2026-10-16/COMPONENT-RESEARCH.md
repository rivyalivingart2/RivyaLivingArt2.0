# Cinematic component and reference research

Research date: 2026-10-16. Scope: the complete public website and private Studio, using the current RivyaLivingArt2.0 architecture. This document records source inspection and integration decisions; it does not certify visual, runtime, legal or device acceptance. No new package was installed and no third-party showcase component was copied by this research task.

## Decision

Reuse the installed GSAP/ScrollTrigger system for scroll-linked media. Implement the cursor lighting as a small shared client controller using refs, CSS custom properties and one scheduled animation loop, with ordinary CSS gradient layers. Keep the existing browser scroll behavior. Existing page, card, media and Studio components remain the rendering owners.

The researched spotlight implementations validate useful patterns: light layers ignore pointer events; content stays in a separate readable layer; interpolation does not require a React render on every pointer event; leaving the surface or hiding the tab clears interactive state. Rivya does not need a second animation library or a WebGL context to produce its requested diffused lighting. This is an engineering choice based on the current scope, not a claim that CSS gradients are always cheaper than shaders.

Current manifest evidence: Next 16.3.5, React/React DOM 19.3.0, GSAP 3.15.0, `@gsap/react` 2.1.2, Radix 1.6.7, Tailwind 4.3.3. Motion, Three.js and OGL are not current production dependencies. Compatibility statements below concern inspected upstream manifests or documentation, not an installation/build of those candidates.

## Selected implementation principles

1. **One lighting runtime per rendered shell.** Public `ShopShell` and private `Workspace` own their respective scopes. Avoid a second app frame or nested active spotlight loops. Saved previews render through their real page templates.
2. **No pointer-driven React state.** Pointer events update target coordinates in refs; the scheduled frame interpolates current coordinates and writes a few CSS properties. React state may handle explicit preferences, not every mouse movement.
3. **Transform a diffused layer.** Use a fixed-size radial light whose position changes through transforms where practical. Avoid continuously changing every section's complete background image. Profile the result; “GPU-friendly” is not proof of low cost.
4. **Coordinate activity and visibility.** Only visible eligible surfaces receive live treatment. Release listeners/observers/RAF on unmount; stop activity while the tab is hidden. Idle movement should be slow and low-opacity, and absent in reduced-motion mode.
5. **Keep purpose-specific presets.** Hero/media: very restrained spotlight plus strong reading scrim. Story/gallery: gentle blue/gold light. Policies/FAQs/forms: calm reading surfaces. Studio: low-intensity shell lighting, with no parallax behind fields, data tables or operational controls.
6. **Preserve input and focus.** Decorative layers use `pointer-events: none` and remain out of the accessibility tree. Never replace the native cursor. Gradients cannot be the only indication of hover, focus, selection or errors.
7. **Separate media movement from playback.** Retain poster-first rendering, approved media, muted inline video, pause controls, reduced-motion and touch behavior. Motion fallbacks must work even if a video does not play or a browser lacks the new effects.
8. **Use content-safe height.** Shared fullscreen sections use minimum viewport height and may grow. Product grids, policy prose, FAQs, forms and Studio operational interfaces keep natural height. Full-bleed scene media must not distort product evidence.
9. **Use existing dependencies.** The source comparison provides ideas and pitfalls; implementation should remain locally authored and adapted to existing components. If a future change copies MIT source, retain its licence/attribution rather than relying on this research note.

These are implementation criteria. Actual completion, package changes, screenshots and performance/accessibility results belong in the final implementation report and QA receipts.

## Research limits and verification handoff

- Licence statements record the linked sources as inspected on 2026-10-16. No external source code was incorporated by this research task. Candidate versions/licences can change; preserve exact evidence if adopting a candidate later.
- No claim is made that an uninstalled library was tested with Next 16.3.5 or this application. Peer ranges and official guides are screening evidence only.
- No WebGL effect or third-party demo media is required. Existing approved library and Drive-register assets remain the media source of record; this research did not upload, reassign or publish assets.
- Browser screenshots, mobile/touch behavior, contrast, reduced motion, pointer reset, offscreen activity and bundle/runtime cost must be checked against the implemented result. Source inspection alone does not complete them.
- Full route and section coverage is recorded in `ROUTE-AUDIT.md` and `route-audit.json`. Those are inventory/coverage targets; the final report must distinguish source coverage, automated evidence and any remaining human/device checks.
