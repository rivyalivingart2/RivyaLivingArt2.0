Rivya Living Art · Proposal · 13 October 2026

A complete new website and Studio design.

Seven approval-gated phases to introduce modern layouts, imagery, video, parallax and smooth interactions while preserving Rivya’s brand, content and working platform.

Status: report only — implementation has not started.
Approval of this plan does not automatically approve every phase. Start Phase 1 only after the owner approves it; stop after each phase for review and permission to continue. Production publication and release need explicit authorization.

1. Findings and design direction

The inspected checkout is clean at 4cadf21b380a8f3753232318fbb78027aa09ffc5. The existing application uses Next.js 16, React 19, TypeScript, Tailwind 4, Radix and Tiptap. Its Studio navigation contract contains 37 workspaces. GSAP skills are installed as guidance; GSAP and its React integration are not yet application dependencies.

The latest stored verification checkpoint describes 781 public routes, 120 published products, 535 content records including the 480 editorial entries, and 373 media URLs. These are historical checkpoint figures, not a fresh production recount for this report. Phase 1 will establish the current preservation baseline, including the existing orders and labelled training inquiries.

Proposed direction: a contemporary material gallery. Use large, carefully cropped material photography; generous editorial spacing; asymmetric compositions; clear product detail; alternating full-width imagery and focused reading sections; and restrained champagne accents. Retain the existing font families initially and redesign their hierarchy and scale, with Hindi/Gujarati layout checks. Studio should use the same brand through a clearer navigation frame, compact readable tables, contextual side panels and better separation of editing, preview and publication.

The latest brief replaces the earlier requirement to copy OLDWEBSITE visually. Existing registers remain useful for coverage and preservation; old page compositions are no longer the design target. Every current section will receive a new presentation treatment. Content can move within an approved composition but cannot silently disappear or be rewritten.

4. Motion and technical approach

ExperiencePlanned treatmentAcceptance boundary
Homepage / material storytellingShallow image parallax, scroll-linked transitions, staged entrances and one carefully bounded cinematic sequence.Readable initial render, short scroll distances, no compulsory long pinning; static equivalent on reduced motion.
Collection / productSubtle image reveals, pointer-only hover polish, clear gallery transitions and restrained sticky purchase/inquiry context.Touch and keyboard have equivalent controls; product colours and details remain faithful.
Journal / policies / long readingQuiet editorial entrances, comfortable line length, optional progress indicator and smooth anchor navigation.Body text remains still and selectable; anchors, find-in-page, print and browser back work.
StudioFast drawer, dialog, tab and status transitions; clear save feedback; gentle ordering feedback.Native scrolling in tables/forms/editors; keyboard and focus remain stable; no parallax behind working controls.

Use GSAP ScrollTrigger and scoped React integration for the interactions that need them. Prefer CSS for simple states. Prototype one desktop smoothing approach, with native scrolling on touch/reduced-motion paths; do not combine multiple smoothing engines. ScrollSmoother is a candidate for that prototype, not an unconditional dependency decision. Verify modal scroll locking, sticky positioning, hash links and scroll restoration before adoption.

Create shared, typed presentation components and a small motion layer; keep public and Studio styling scoped. Keep data fetching, server rendering, permissions and validation intact. Load motion only on routes that need it, clean up timelines on navigation, avoid layout-property animation, and keep meaningful content visible if scripts fail. Avoid a monolithic animation wrapper around the entire application.

Implementation will also use the installed responsive design, design-system, component architecture, interaction and accessibility/testing skills when their phase needs them. 6. Verification and approval rules

  • Every phase: report what changed, show the local preview, list the affected routes/sections, give verification results, reconcile protected data and save a continuation checkpoint. Ask approval before starting the next phase.
  • Responsive review: cover 320/390/768/1024/1440/1920-pixel representative widths, long and short content, English/Hindi/Gujarati, focus/hover/touch, validation errors, loading/empty states and relevant print views.
  • Performance: use LCP ≤2.5 seconds, CLS ≤0.1 and field INP ≤200 milliseconds as targets. Repeat cold-load measurements with documented conditions; show distribution and outliers. Lab interactions do not constitute field INP or real-user acceptance. Investigate the recorded variable homepage server wait before adding expensive motion.
  • Accessibility: verify semantic structure, contrast, keyboard, focus, dialogs, forms, zoom/reflow and reduced motion. Record automated, emulated and actual human/device observations separately. Earlier “Completed by admin” closures remain historical; they do not prove this new candidate.
  • Release: keep implementation local until explicit authorization. No automatic content publication, production test writes, direct-main push or silent schema replacement. Preserve rollback of presentation separately from business data.
